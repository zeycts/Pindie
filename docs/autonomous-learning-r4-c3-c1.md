# Autonomous Learning R4-C3-C1 — Execution Lease contract

Status: C1 pure contract and C2 standalone durable metadata persistence implemented. No heartbeat timer, stale detection, expiry, recovery, takeover, cancellation, retry, evaluator invocation changes or production wiring is added.

## Schema and meaning

`ExecutionLeaseV1` represents ownership metadata for the authority to continue one EvaluationRun execution. Strict fields are `schemaVersion: 1` (the lease version), UUID-v4 `runId`, nonempty `ownerId` of at most 128 characters, and canonical ISO `acquiredAt` / `heartbeatAt` timestamps. Owner IDs reuse the existing LearningJob owner-length convention and are opaque operational identities, not evaluator/model provenance or authentication credentials. `heartbeatAt >= acquiredAt`; missing/unknown keys, unsupported versions, invalid IDs and noncanonical or reversed timestamps fail closed through `validateExecutionLease`.

`createExecutionLease(running, ownerId)` projects a frozen initial lease from a valid running EvaluationRun: `runId` is exact and both timestamps equal `startedAt`. Created and terminal runs reject. This pure helper does not prove that running was committed or acquire execution authority. All fields are primitive and readonly; no caller reference is retained. Existing `canonicalJson` and `learningFingerprint` conventions give stable bytes/digests for the same metadata regardless of object key order. C1 introduced no dedicated artifact ref or storage namespace; C2 adds these below without changing the ExecutionLease v1 or EvaluationRun schema.

## Ownership and claimExecution

Only one active lease may represent one execution. The existing R4-C3-B `claimExecution` boundary remains the authority acquisition mechanism: under the EvaluationRun namespace lock, only the unique publisher of the immutable running snapshot receives the claim and its exact terminal-publication capability. Competing/replayed claims reject, including identical timestamps. Lease creation is intended for that unique claim owner; validating or copying lease bytes, inventing an owner ID or reading committed running history grants no claim. The contract helper is deliberately not a second ownership registry and cannot independently enforce uniqueness among caller-created values.

C2 adds metadata persistence after a successful claim, without accepting lease bytes as execution authorization or changing ExecutionRunner. `FileEvaluationRunStore` records the live returned claim in a process-local WeakMap only after running publication is acknowledged. `readEvaluationExecutionClaim` verifies that exact object and its resolved projects-root binding; reconstructed or copied claim objects and foreign roots reject. The map stores only claim provenance, has weak ownership and is not a durable registry or recovery mechanism. No replacement claim can be reconstructed after restart or lost acknowledgment. Under the lease namespace lock, `createLease(claim, ownerId)` commits exactly one origin with the claim's exact running ref and start time. An identical create request returns that historical origin, even after heartbeats; a different owner conflicts. The run and lease commits are separate: lease write failure leaves the consumed running claim intact and grants no replay permission. A terminal run has no continuing execution authority, even if an old lease snapshot remains readable. No release/reacquisition or replacement owner is legal in this contract.

## Immutable heartbeat history

`heartbeatExecutionLease(previous, heartbeatAt)` returns a new frozen snapshot and leaves the previous snapshot unchanged. `isExecutionLeaseHeartbeat` independently validates both snapshots and requires identical schema version, run ID, owner ID and acquisition timestamp; only heartbeat time may advance. Equal timestamps are legal identical metadata retries. Backward or invalid times and changed ownership reject. This preserves who owned execution and when ownership began across the complete supplied snapshot chain; no helper rewrites prior history. These are the unchanged pure C1 rules. C2 persistence requires strict advancement as described below.

Heartbeat timestamps describe operational progress reports only. They imply no expiration duration, deadline, timeout, liveness proof or right to reclaim. C2 now supplies durable heartbeat metadata with exact predecessor and identity checks. Stale detection still needs a separately approved clock/threshold policy and execution-authority fencing. Recovery, takeover and retry need their own explicit authority rules; an old/missing heartbeat alone cannot replay evaluator execution. Lost claim acknowledgment or process death retains the existing consumed running attempt without replacement ownership.

## Capability boundary

Lease values expose only metadata and grant no Strategy mutation, Policy mutation, Trust mutation, Decision authority, EvaluationResult publication, evaluator invocation or terminal-publication capability. The pure contract module performs no I/O. The separate store writes only its lease namespace and receives no semantic store or evaluator capability. Neither is imported by production composition or ExecutionRunner. The live-claim provenance reader supplies metadata only and does not invoke the claim's terminal writer. Owner strings are metadata identities, not authentication secrets; exact-ref heartbeat checks are consistency fences, not a sandbox for hostile callers. Frozen values and strict shape validation protect the supplied interface; they are not a process sandbox or proof of an owner's identity.

Tests cover valid creation/lifecycle placement, missing/unknown fields, malformed IDs/owners/times/versions, deterministic serialization/fingerprints, immutable owner/acquisition identity, monotonic and identical heartbeats, and absent mutation/execution capabilities. Existing run-store/runner tests retain exclusive claim and immutable lifecycle coverage.

## C2 durable persistence boundary

`ExecutionLeaseStore` / `FileExecutionLeaseStore` exposes `createLease(claim, ownerId)`, `heartbeat(previousExactRef, nextLease)`, `get(exactRef)` and `getCurrent(projectId, runId)`. Returned snapshots contain detached deeply frozen lease metadata, exact running ref, previous fingerprint and a dedicated `ExecutionLeaseRef` (`schemaVersion: 1`, family `execution-lease`, project ID, run ID, whole-content fingerprint). This ref is outside EvaluationRef and LearningArtifactRef and grants no execution/trust/Decision authority. Historical exact lookup never substitutes current metadata and needs neither live run nor packet availability.

Project-local `learning-v1/execution-leases-v1/<runId>.<digest>.json` contains canonical `{ schemaVersion: 1, lease, runningRef, previousFingerprint, fingerprint }` envelopes. The SHA-256 fingerprint covers schema, all lease fields, exact running binding and predecessor. Origin has a null predecessor and heartbeat equal to acquisition/start time. Each heartbeat links the preceding whole-content digest. The current snapshot is derived from complete validated history; there is no mutable pointer, overwrite or database abstraction.

Under this namespace's existing `FileGlobalWriterLock`, writes validate the entire bounded history, then exclusively write a temporary file inside `writer.lock/`, sync/close and verify bytes, uniquely hard-link the final file and sync the directory. Metadata is detached before the first await. At most 4096 snapshots per project and 4KiB per artifact are allowed; capacity fails closed without pruning or rewriting history. Invalid versions/shapes, noncanonical bytes, digest/filename/project/run mismatches, malformed filenames, missing origins/predecessors, branches, changed identity/binding and nonmonotonic histories reject reads and writes. Store writes do not touch EvaluationRun artifacts, Experience, Strategy, Policy, Trust, Decision or result namespaces.

`heartbeat(previousExactRef, nextLease)` requires the supplied ref to equal the current committed snapshot under lock, preserves `runId`, `ownerId`, `acquiredAt` and running binding, and requires `next.heartbeatAt > current.heartbeatAt`. Equal and older timestamps reject, including identical durable heartbeat retries and competing writes from the same predecessor. C1's pure helper may construct equal-time values, but those values cannot advance durable history. Exact lookup/current inspection can reconcile a committed-but-unacknowledged heartbeat; this does not retry evaluator execution.

A pre-link failure exposes no snapshot; a lost acknowledgment after linking may leave a valid committed snapshot. Identical origin publication reconciles safely. Heartbeat callers reconcile through exact/current lookup rather than republish from a stale predecessor. No atomic run-plus-lease transaction, automatic lease creation in ExecutionRunner, timer, expiry or claim release is implemented. Historical metadata may be recorded/read after a run becomes terminal; this does not authorize continued execution. Normal run lifecycle remains the execution truth.

ExecutionLease persistence is implemented, but stale detection and recovery remain future work.

C2 tests cover genuine-claim/root binding, deterministic bytes across independent histories, exact and current restart lookup, strict heartbeat advancement and identity preservation, competing origins/heartbeats, immutable linked history, corrupt/schema-invalid/noncanonical/oversized artifacts, missing predecessors, pre/postcommit failures, detached inputs, capability isolation and unchanged run/semantic namespaces. EvaluationRun and ExecutionRunner regression tests retain the execution-authority guarantees.
